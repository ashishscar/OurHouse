# OurHouse AI app care

The private `ourhouse-care` Worker runs a SQLite Durable Object and Workers AI. It has no public route, family database, receipt bucket, account key, OAuth credentials or deployment credentials. The public app calls it through `CARE_SERVICE`; only verified signed-in, same-origin requests can ask for a check or submit a fixed technical code. Public status reads do not run checks or inference.

Every five minutes it checks the generic public health endpoint, three fingerprinted public scripts and synthetic recipe/receipt examples. Inference receives only the release number, check outcomes, fixed technical categories and counters. Raw errors and household content are excluded. Eight short AI reviews per UTC day are shared across the entire app; the budget survives code releases.

Automatic tools are prewritten and bounded: protect confirmed faulty recipe/receipt entry, restore after two healthy scans, and request fingerprint-verified public cache repair. Network failures and mismatched deployment releases do not trigger entry protection. Browser cache repair never clears account storage, drafts or pending writes and never reloads the page. New source defects are recorded for a tested release; the model cannot publish code, run SQL or alter family records.

## Release procedure

1. Make the source changes and bump the app release in `lib/http.mjs`, the manifest release generated by `scripts/prepare-ui.mjs`, and the manual edition where applicable.
2. Run `scripts/prepare-ui.mjs` before the framework build. It regenerates the watched public-file hashes. Run the relevant tests, type check and build, then save/package the exact source through the existing source workflow.
3. Deploy `maintenance/wrangler.json` to the existing Cloudflare account. For a new installation, initially omit the cron until the matching app is live. This configuration intentionally grants no family-data bindings.
4. Deploy the public Worker with the `CARE_SERVICE` service binding in `standalone/maintenance-bindings.json`, keeping the existing DB, assets, secrets and notification/cleanup cron. Do not replace or rotate account keys.
5. Enable the care worker's five-minute cron and verify `/api/health`, exact deployed public-file hashes, and `/api/maintenance`. A release mismatch is an inconclusive probe, not evidence that a public file is corrupt.
6. Verify a real AI review and a scheduled check without pressing Run health check. Do not claim the production model is working based on a local stub. Keep raw request logging disabled.

The maintenance worker can be rolled back independently of the family app. An unavailable care service leaves working entry tools available. Never use a rollback or recovery action to clear live household storage.
